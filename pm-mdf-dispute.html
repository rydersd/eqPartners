⚙ Wireframe Spec — pm-mdf-dispute.html

Persona

Steve Rogers — AE, CloudBridge Solutions. Partner PM role

Steve submitted a POP for AWS re:Invent co-sponsorship in January. His PAM (Alex Rivera) rejected it citing an un-itemized invoice. Steve believes the documentation is clear enough — or can be supplemented — and wants to dispute rather than abandon the $8,500 claim.

Why this screen exists

In the prior wireframe set, Steve could submit a POP via pm-pop-submission.html and Alex could reject it via pam-mdf-claims.html. But there was no screen for what Steve sees after rejection — the claim disappeared from his view with no recourse. This is the dispute entry point, analogous to pm-tier-appeal.html in the tier demotion flow.

Design decisions

  • Rejection reason surfaced prominently: The PAM's note is quoted verbatim at the top. Steve should understand exactly what failed before filling out a dispute form — not discover it buried in a detail table.
  • Document status per file: Each POP file is marked accepted or flagged individually. This tells Steve which asset caused the rejection without ambiguity.
  • "Partial approval" as a resolution option: Real-world partner oracles indicate that many MDF disputes settle on a lower approved amount. Offering partial approval as an explicit option reduces round-trip negotiation and anchors the conversation constructively.
  • Suggested additions callout: Tells Steve what supplementary docs would likely fix the rejection (signed co-branding agreement, itemized line). This is an education moment built into the flow rather than requiring Steve to go read guidelines separately.
  • Guideline reference in sidebar: Cites the specific MDF requirement (3.2) that triggered the rejection and offers the alternative (vendor letter). Reduces follow-up support tickets.
  • Escalation path visible in timeline: If PAM denies again, Steve can escalate to Priya (CMM). This path is disclosed up front so Steve knows his options before committing to the dispute. One escalation per claim prevents abuse.
  • Claim paused on submission: The timeline states the original rejection is paused once a dispute is submitted. This matters — Steve should not fear that a clock is running against him during the review period.

Counterpart screens

  • pam-mdf-claims.html — Alex's screen where the rejection originated; dispute routes back here
  • pm-pop-submission.html — original POP upload; Steve's starting point
  • cmm-mdf-oversight.html — Priya's escalation queue if PAM denies again
  • pm-tier-appeal.html — structural analogue (partner appeals an adverse Equinix decision)

MDF chain context

This screen closes the loop on the full MDF lifecycle: Priya sets budget → Steve checks balance → Steve requests → Alex approves → Steve executes → Steve submits POP → Alex reviews → Steve disputes rejection (this screen) → Alex or Priya decides → reimbursement issued.

Accessibility notes

  • Rejection notice uses role="alert" and aria-label for screen reader announcement.
  • Upload zone is keyboard-focusable with role="button" and tabindex="0".
  • Timeline uses role="list" / role="listitem" and decorative dots are aria-hidden.
  • Character count is aria-live="polite" to announce dynamically without interrupting flow.
  • All required fields have aria-required="true" and visible * markers.
