Summary

Pre-authentication page reached from the tokenized link in the acceptance email. The user sets up their authentication method (SSO or TOTP), saves recovery codes, and is redirected to the onboarding wizard.

Flow Position

Registration chain: Apply → Confirmation → Acceptance Email → Auth Setup (this) → Onboarding Wizard

Jobs to Be Done

  • Establish a secure, user-owned credential (not just email magic links)
  • Offer SSO as the low-friction path; TOTP as the fallback
  • Confirm the user's identity is tied to their work email domain
  • Surface recovery codes before first login — users who skip this get locked out
  • Get the user to the onboarding wizard without unnecessary friction

Design Specification

Primary Content

  • Verified badge confirms invitation token is valid (checked on page load)
  • Step 1: Auth method selector — SSO (recommended) vs Authenticator App (TOTP)
  • SSO sub-panel: Google and Microsoft provider buttons
  • TOTP sub-panel: app download links, QR code, manual key, 6-digit code entry
  • Step 2 (recovery): 6 single-use recovery codes, copy/download actions, confirm-saved checkbox gates the CTA

Interactive Elements

  • Method radio selector (SSO / TOTP) — shows/hides relevant sub-panel
  • SSO provider buttons (Google, Microsoft) — trigger OAuth redirect
  • TOTP digit boxes — keyboard-navigable, auto-advance on input
  • Verify & Continue — validates TOTP code, reveals recovery card
  • Copy codes / Download .txt buttons
  • Saved checkbox — enables "Go to Onboarding" button when checked

Functionality

  • Token validation on page load — invalid/expired tokens redirect to error page with re-send option
  • SSO flow: standard OAuth PKCE, scoped to user email domain
  • TOTP: TOTP secret generated server-side, displayed as QR + base32 key; verified against current time window ±1 step
  • Recovery codes: generated server-side, bcrypt-hashed in DB, displayed once
  • On successful setup, session established → redirect to onboarding-wizard.html
  • SSO path skips Step 2 (recovery) — recovery handled by IdP

Design Notes

  • SSO marked as "Recommended" because it has better recovery paths and lower support burden
  • TOTP QR code in wireframe is a decorative placeholder — production generates per-user TOTP secrets
  • Digit boxes are a wireframe affordance; production implementation uses a single <input type="text" inputmode="numeric" maxlength="6"> with visual styling
  • Recovery card only appears after TOTP verification (SSO users don't need it)
  • Checkbox on recovery step is a soft gate — forces acknowledgment but users could technically skip via keyboard
  • Page is intentionally minimal — single column, no nav clutter — to maximize completion rate at this high-drop-off step
